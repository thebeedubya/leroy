# 72 Tests, Zero Failures, No Humans in the Loop

I built an AI engineering lead named Leroy. Yesterday I told him to QA his own A2A server. He decomposed the job into five parallel agents, each owning a test category. They ran concurrently and reported back structured results. 72 tests. Zero failures. I did not write a single test.

## What Got Tested

The test battery covered everything: agent card verification, authentication (valid, invalid, missing tokens), full task lifecycle (submit, status transitions, completion), error handling (malformed specs, empty specs, oversized specs), bidirectional messaging, MCP client tools, concurrency, and persistence. Not a smoke test. A real QA suite.

Five agents ran in parallel:
- Agent Card + Health + Auth (15 tests)
- Task Lifecycle + Listing (13 tests)
- Error Handling + Cancellation (13 tests)
- PM Bidirectional Messaging (13 tests)
- MCP Tools + Concurrency + Persistence (18 tests)

Total execution time: 456 seconds. Under 8 minutes for a comprehensive QA pass.

## What This Actually Means

The interesting part is not that the tests passed. The interesting part is the decomposition pattern. Leroy did not run 72 tests sequentially. He looked at the spec, identified natural test boundaries, spawned specialized agents for each boundary, and ran them in parallel. That is how a senior QA lead thinks, not how a test script runs.

Three of the five agents independently flagged the same low-priority finding: task IDs are embedded in human-readable text instead of a structured JSON field. They did not coordinate on this. They each discovered it through their own testing. Convergent findings from independent agents is a signal-quality indicator you do not get from a single test runner.

## The Broader Pattern

This is the third validation point in a pattern I am seeing: agents are better at testing other agents than humans are. Not because they are smarter. Because they are faster, they do not get bored, they do not skip edge cases, and they can run in parallel without context switching.

The role of the human in this loop is not writing tests or running them. It is deciding what to test and whether the results matter. Product judgment, not test execution. That is where the leverage is.

## What I Would Change

The spec could have been more specific about expected response formats. The task ID extraction issue exists because I did not specify the contract tightly enough. That is a spec quality problem, not an engineering problem. When your AI engineering lead is good enough to pass 72 tests, the bottleneck moves upstream to spec quality.

That is where it should be.

# Four Production Deployments in One Day With an AI Engineering Team

Yesterday I shipped four things to production. Persistent task store with SQLite WAL mode. A task retention policy that never deletes completed work. A dashboard with kanban board, drill-down, and server-sent events for live updates. And a validated PM-Ops team pattern where a coordinator agent catches deliverables and status changes automatically.

I am one person. I do not write code. I write specs.

## How This Works

I run an AI product management layer called FORGE. My PM agent (running in Claude Desktop) writes specs. My engineering lead (Leroy, running in Claude Code) decomposes and executes them. An ops agent handles configuration and cross-cutting concerns. They communicate over the A2A protocol.

My job is deciding what gets built and whether it meets the bar. Their job is figuring out how to build it and actually building it.

## What Shipped

**Persistent task store.** Every task Leroy receives now survives server restarts. SQLite in WAL mode. Before this, restarting the A2A server wiped the task queue. Now there is a durable record of every spec sent, every result returned, every failure logged.

**Task retention policy.** Completed and failed tasks are never deleted. This sounds obvious but it matters for retrospectives. Every completed spec is a learning artifact. Deleting them is deleting institutional memory.

**Dashboard v1.** Kanban board with pending, working, and completed columns. Click any task for full drill-down: spec text, result, timestamps. SSE live updates so the board moves in real time as Leroy works. No polling. No refresh button.

**PM-Ops team pattern.** The coordinator daemon watches for status changes and catches deliverables without me polling. When Leroy finishes a task, the system routes the result to the PM inbox. I review when I am ready, not when I happen to check.

## The Compounding Effect

None of these individually are impressive. SQLite WAL is not novel. Kanban boards exist. The point is that all four shipped in one day because the bottleneck is spec quality, not engineering capacity.

When you have an AI engineering team that can decompose, build, and validate work autonomously, the constraint shifts to the product layer. How fast can you write good specs? How clearly can you define acceptance criteria? How quickly can you review and approve?

Those are product management skills, not engineering skills. That is the unlock.

## What Is Next

The dashboard needs a completed tasks column fix. The coordinator needs true daemon behavior instead of idle-after-check. And the big one: Leroy needs to pick up specs automatically instead of waiting for a manual prompt. All of those are specs I will write this week.

The machine keeps getting faster. The specs keep getting better. The compounding is real.
